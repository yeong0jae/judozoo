# 023 — Cloudflare 프록시 → GCP 부하 분산기 전환

Goal: 한국 사용자가 **서울 VM에 가려고 태평양을 왕복하지 않게** 만든다.
입구를 Cloudflare 프록시에서 GCP 전역 외부 애플리케이션 부하 분산기(+ Cloud CDN)로 옮긴다.
Cloudflare는 DNS만 남는다.

> **로딩 표시를 개선하는 작업이 아니다.** 흰 화면을 가리는 인라인 배경색 같은 건 이 문서의
> 범위가 아니다 — 대기 시간이 그대로인 채 아래의 원인 신호(흰 화면 = CSS 미도착)만 지운다.

## 진입 조건 (2026-09-25 실측)

### 제보

"처음 들어오는 사람·오랜만에 온 사람은 첫 화면이 20초 넘게 하얗다." 화면 녹화 한 편
(데스크톱, 맥 Chrome, 주소 직접 입력) — 약 20초 흰 화면 뒤 어두운 화면이 뜨고, 그 뒤 데이터가 채워진다.

### Cloudflare Web Analytics에 그 방문이 그대로 남아 있었다

18:25~18:30 KST, 한국 · MacOSX · Chrome · 직접 · `/`. 같은 6시간의 나머지 방문은 전부 7초 이하,
전체 페이지 로드 중앙값은 1,845ms.

| 구간 | 값 | 읽는 법 |
|---|---|---|
| DNS | 10ms | 정상 |
| TCP | 266ms | 정상 |
| 요청 + 응답 (HTML) | 1,179 + 347ms | **HTML은 빨리 왔다** |
| **처리 중** | **35,970ms** | HTML 수신 이후 — CSS·JS·폰트를 받고 실행한 구간 |
| **첫 콘텐츠 페인트** | **23,860ms** | 영상의 흰 화면 길이와 맞는다 |

### 흰 화면 = CSS가 아직 안 온 상태

- 어두운 배경은 외부 CSS의 `body { background-color: var(--page-bg) }`(`src/index.css`)에서만 나온다.
  `index.html`의 인라인 스크립트는 `dark` 클래스만 붙인다
- 모듈 JS는 defer라 첫 페인트를 막지 않는다. **첫 페인트를 막는 건 `index-*.css` 하나다**
- 앱에는 전역 인증 관문이 없다(`App.tsx`). `useMe()` 로딩 중 숨는 건 계정 버튼뿐이다

→ **인증·API·백엔드 콜드 스타트는 흰 화면의 원인에서 빠진다.** 셋 다 CSS가 온 뒤의 일이고,
그랬다면 흰 화면이 아니라 어두운 빈 화면이 보였어야 한다.

### 한국에서 붙는 Cloudflare 지점이 LA다

영상을 찍은 PC에서 `https://judozoo.com/cdn-cgi/trace` → **`colo=LAX`**.

```
한국 사용자 ──태평양──▶ Cloudflare LA ──태평양──▶ GCP 서울 VM
```

- 같은 맥·같은 LA 경로로 새 Chrome 프로필 측정: 첫 페인트 2.1초, 마지막 API 2.8초.
  재방문(브라우저 캐시 있음): 0.1초 / 0.9초. **항상 느린 게 아니라 간헐적으로 크게 느려진다**
- 작은 HTML(3.7KB)은 빨랐고 큰 파일만 늦었다 — 손실 있는 장거리 경로의 전형적인 모양이다
- 방문자가 적어 LA 지점 캐시가 자주 비어 있다(`cf-cache-status: MISS`) — 그러면 LA가 서울 원본까지
  **태평양을 한 번 더** 건넌다
- 재방문자는 CSS·JS를 브라우저 캐시에서 꺼낸다(12~25ms). **신규·장기 미접속에 몰리는 이유가 이것이다**

> **검증되지 않은 부분:** 23초를 만든 게 패킷 손실인지 LA 지점의 원본 fetch인지는 가르지 못했다.
> 어느 쪽이든 태평양 경로 위의 일이고, 이 작업은 경로 자체를 없앤다. §5의 비교 측정이 판정이다.

### 함께 발견한 것: HTML에 `Cache-Control`이 없다

HTML 응답에 `last-modified`만 있어 브라우저가 **휴리스틱으로 캐시한다**(재방문 측정에서 `/`가 1ms).
배포 뒤 옛 HTML이 사라진 해시 자산을 가리키면 **404 → 화면이 영영 빈다**(없는 해시 요청이
404인 것 확인). 이번 증상("20초 뒤 뜬다")과는 모양이 달라 원인으로 보지 않지만, §3에서 같이 막는다.

## 설계 결정

| 항목 | 선택 | 이유 |
|---|---|---|
| 입구 | **전역 외부 애플리케이션 부하 분산기** | 구글은 한국 통신사와 직접 연결돼 서울에서 구글 망에 들어온다. 이후 VM까지 구글 내부망 |
| 정적 파일 캐시 | **Cloud CDN, `USE_ORIGIN_HEADERS`** | nginx가 헤더로 캐시 여부를 정한다. `CACHE_ALL_STATIC`은 확장자로 추측해서 022의 `robots.txt` 사고를 다시 부른다 |
| 인증서 | **Certificate Manager 관리형 + DNS 인증** | DNS를 넘기기 **전에** 발급받아 둘 수 있다. 로드밸런서 인증 방식은 DNS가 이미 가리켜야 발급돼서 전환 순간 TLS가 빈다 |
| 인증서 개수 | **최종 1개** | 지금은 Cloudflare 엣지 + Caddy Let's Encrypt 2개. 부하 분산기 → VM 구간은 구글 망 안이라 HTTP |
| Caddy | **제거** | TLS를 부하 분산기가 맡으면 할 일이 없다. `AT_CLOUDFLARE_API_TOKEN`·인증서 볼륨도 같이 빠진다 |
| HTTP → HTTPS | URL 맵 리다이렉트 전용 HTTP 전달 규칙 | Caddy가 자동으로 하던 일 |
| 원본 숨기기 | 방화벽을 **구글 부하 분산기 대역**(`130.211.0.0/22`, `35.191.0.0/16`)만 | 드러나는 건 부하 분산기 IP — 구글의 입구라 VM 우회로가 아니다. `security.md` 규칙 3의 취지 유지 |
| 실제 방문자 IP | 백엔드 서비스 **커스텀 요청 헤더** `X-Client-IP: {client_ip_address}` | `CF-Connecting-IP`처럼 단일 값이다. XFF는 `클라이언트, 부하분산기IP` 모양이라 부하 분산기 IP까지 신뢰 목록에 넣어야 한다 |
| 전환 기간의 두 입구 | **Caddy가 `CF-Connecting-IP`를 `X-Client-IP`로 옮겨 싣는다** | 헤더가 하나로 맞아 nginx `real_ip_header`가 한 줄로 끝난다. `map`으로 입구를 가르는 것보다 단순하고, 정리 때 Caddy와 함께 사라진다 |
| 압축 | 백엔드 서비스 `compression_mode = "AUTOMATIC"` | Cloudflare가 해주던 brotli다. nginx에 gzip 설정이 없어서, 빠뜨리면 JS 673KB가 그대로 나간다 |
| 호스트 포트 | nginx가 **`3000`을 직접 퍼블리시** — `docker-compose.prod.yml`에만 | 앱 VM의 3000은 비어 있다(Grafana는 019에서 ops VM으로 갔다). 기본 compose에 두면 로컬에서 ops compose의 Grafana와 부딪힌다 |
| 상태 확인 | nginx `location = /healthz` (`access_log off`) | `/`를 쓰면 프로버 여러 대의 요청이 Loki에 쌓인다 |
| 백엔드 타임아웃 | 기본 30초 유지 | 브로커 대기 상한이 20초라 안에 든다 |
| DNS | **Cloudflare에 남김**, 회색 구름 | 조회는 작은 패킷 한 번이고 통신사 리졸버가 캐시한다. 느린 방문에서도 10ms였다 |
| DDoS·WAF | **이번엔 붙이지 않는다** | Cloud Armor는 필요가 확인되면. 대신 잃는다는 사실을 적어둔다 |
| 실사용자 측정 | Cloudflare Web Analytics **JS 스니펫을 `index.html`에 직접** | 프록시가 꺼지면 자동 삽입이 끊긴다. 이번 원인을 잡은 도구라 전후 비교에 반드시 필요하다 |
| 브로커용 고정 IP | **건드리지 않는다** | `google_compute_address.frontend`는 **나가는** 키움·KIS 호출용이다. 부하 분산기는 들어오는 쪽만 바꾼다 |
| 되돌리기 | 전환 후 **1주**는 Caddy·Cloudflare 대역을 살려둔다 | 되돌리기 = DNS를 다시 주황 구름으로. 그동안은 방화벽에 두 대역이 함께 열린다 |

## 알려진 함정

- **인증 CNAME이 Caddy의 인증서 갱신을 막는다.** Caddy도 `_acme-challenge.judozoo.com`에 TXT를
  만들어 DNS-01로 갱신하는데, 같은 이름에 CNAME이 있으면 TXT를 둘 수 없고 Let's Encrypt는 CNAME을
  따라가 실패한다. 당장은 유효하지만 **되돌리기용 Caddy 경로의 수명이 남은 인증서 기간으로 묶인다.**
  전환과 정리를 몇 주 안에 끝낸다.
- **배포 순간 짧은 창.** frontend(nginx)가 caddy보다 먼저 바뀌면 `X-Client-IP`가 없는 요청이 잠깐
  들어와 방문자 IP가 Caddy IP로 찍힌다. 몇 초짜리라 받아들인다.

- **실제 IP 복원을 틀리면 조용히 망가진다.** 에러는 안 나고, `limit_req`가 모든 방문자를
  부하 분산기 한 IP로 묶어 한 명이 상한을 채우면 나머지가 429를 받는다. 2026-09-18에 Caddy 뒤에서
  한 번 밟은 함정이다(`nginx.conf` 주석).
- **XFF에는 부하 분산기 자기 IP가 붙는다.** `클라이언트, 부하분산기IP` 모양이라 `35.191.0.0/16`만
  신뢰하면 부하 분산기 IP를 방문자로 읽는다. 커스텀 헤더를 고른 이유다.
- **인증서는 DNS가 가리켜야 발급된다(로드밸런서 인증 방식).** 그래서 DNS 인증 방식을 쓴다.
  CNAME을 지우면 갱신이 실패한다 — Cloudflare DNS를 손볼 때 조심한다.
- **Cloudflare RUM이 끊긴 채 전환하면 효과를 증명할 수 없다.** §4를 전환보다 먼저 한다.
- **Cloudflare 보호가 사라진다.** 부하 분산기 IP는 공개 정보다. 문제가 생기면 Cloud Armor를 붙인다.
- **CDN 캐시 무효화.** HTML은 캐시하지 않으므로 배포 때 따로 할 일이 없어야 정상이다.
  옛 HTML이 보이면 헤더 설정부터 의심한다.
- **HTTP 리다이렉트는 공짜가 아니다.** 전달 규칙이 하나 더 필요하다(5개 묶음 안이라 비용 증가는 없다).
