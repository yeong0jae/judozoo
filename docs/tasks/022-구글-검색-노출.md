# 022 — 구글 검색 노출 (기술 SEO 토대)

Goal: 구글이 judozoo를 **발견하고, 화면을 구분해서 읽고, 결과를 수치로 되돌려주는** 상태까지 만든다.
지금은 셋 다 없다 — sitemap이 없어 발견 경로가 없고, 모든 경로가 같은 HTML이라 구분이 안 되고,
서치콘솔이 없어 색인이 됐는지조차 모른다.

> **왜 콘텐츠가 아니라 토대부터인가.** "무슨 글로 승부할지"(설명 페이지 / 공개 데이터 페이지 /
> 게이트 완화)는 이 다음 문서의 질문이다. 지금 그걸 고르면 **근거가 감뿐이다** — 현재 색인된
> 페이지 수도, 노출되는 검색어도, 구글이 렌더에 실패하고 있는지도 모른다. 아래 작업은 어떤
> 콘텐츠 전략을 고르든 **어차피 전부 필요하고**, 끝나면 서치콘솔에 숫자가 쌓이기 시작한다.
> 3~4주 뒤 그 숫자를 보고 다음을 정한다.
>
> **대신 정직하게** — 이 문서의 작업만으로 오는 유입은 대부분 **브랜드 검색**(`judozoo`)이다.
> 모르는 사람을 새로 데려오는 건 콘텐츠의 몫이고, 여기서는 안 된다.

## 진입 조건 (2026-09-18 실측)

### 배관이 전부 비어 있다

```
curl https://judozoo.com/robots.txt   → 200, 본문은 <!doctype html>
curl https://judozoo.com/sitemap.xml  → 200, 본문은 <!doctype html>
curl https://judozoo.com/aaaa-none    → 200
```

셋 다 `nginx.conf`의 `try_files $uri /index.html`이 index.html을 내준 것이다.

| 항목 | 현재 | 결과 |
|---|---|---|
| `robots.txt` | 없음 (HTML 200) | sitemap을 알릴 자리가 없다 |
| `sitemap.xml` | 없음 (HTML 200) | **구글이 URL을 발견할 경로가 없다.** 외부 링크가 거의 없어 우연한 발견도 기대 못 한다 |
| 없는 경로 | **200 + index.html** | 오타·옛 링크가 전부 유효한 페이지로 보인다. 구글은 이걸 soft 404로 분류한다 |
| `<title>` | 정적 HTML은 전 경로 동일. JS가 나중에 바꾼다 (`useTabTitle`) | 렌더 전에는 구분이 안 된다 |
| `description`·`og:*` | **전 경로 공통** (`index.html`에 하드코딩) | 검색 결과 설명이 전부 같다. **카톡·슬랙은 JS를 안 돌려서 어느 화면을 공유해도 첫 화면 소개글이 뜬다** |
| `canonical` | 없음 | `/market-analysis`와 `/market-analysis/kospi`가 같은 화면인데 별개 URL로 보인다 |
| JSON-LD | 없음 | 사이트 이름·로고를 구글에 말해주는 구조화 데이터가 없다 |
| 서치콘솔 | **미등록** | 색인 수·노출 검색어·렌더 실패 여부 전부 관측 불가 |

### 나쁘지 않은 것 (확인해둔 것)

- **`www` 레코드가 없다** — 호스트 중복(`www` vs apex) 문제가 애초에 없다. canonical이 단순해진다
- **Googlebot UA로 200이 온다** — Cloudflare 봇 보호가 크롤러를 막고 있지 않다
- `lang="ko"`, viewport, apple-touch-icon, og:image(1200×630)는 이미 있다

### 색인 대상 경로 (현재 라우트 전부)

| 경로 | 로그인 | 크롤러가 실제로 보는 것 |
|---|---|---|
| `/` | 공개 | 지수·주도주 요약. 숫자 위주 |
| `/market-analysis/{7개 슬러그}` | 공개 | 지수 시세·차트·투자자 수급 |
| `/market-analysis` (슬러그 없음) | 공개 | **`/market-analysis/kospi`와 같은 화면** (localStorage 없으면 기본값) |
| `/leading-stocks` | **게이트** | 목록은 공개지만 종목 상세는 로그인 안내문 |
| `/signal-log` | **게이트** | 미리보기 몇 건 + 로그인 안내문 |
| `/breakout-radar` | **게이트** | 상위 몇 개 + 로그인 안내문 |
| `/privacy` · `/terms` | 공개 | 유일하게 글자가 많은 화면 |

슬러그 7개는 `frontend/src/lib/indices.ts`의 `INDICES`가 정의한다 —

## 설계 결정

| 항목 | 선택 | 이유 |
|---|---|---|
| 렌더링 | **빌드 시 경로별 정적 HTML — `<head>`만** | SSR 도입은 이 규모에 과하다. 게다가 본문은 장중 실시간 값이라 **구워두면 곧 거짓이 된다.** 검색 결과·링크 미리보기에 뜨는 건 `<head>`고, 거기만 정확하면 된다. 본문은 지금처럼 JS가 그린다 |
| 404 | nginx `try_files $uri $uri/index.html =404` | 위 결정으로 경로마다 디렉터리가 생기므로 **알려진 경로 목록을 nginx에 또 적지 않아도** 자연히 갈린다 |
| 404가 딥링크를 깨는 것 | **빌드가 막는다** — `App.tsx`의 `<Route path>`를 훑어 SEO 목록에 없으면 빌드 실패 | 라우트를 더하고 SEO 목록을 안 더하면 그 화면은 **직접 접속 시 404**가 된다. 사용자에게 가기 전에 빌드에서 걸린다 |
| SEO 문구의 출처 | `seo.json` 한 벌 (경로 · title · description) | `build-mark.mjs`가 `mark.json`을 쓰는 것과 같은 방식. **`NAV`의 라벨과 공유하지 않는다** — 메뉴 라벨은 레일 폭 때문에 4자고, 검색 결과 제목은 문장이라 목적이 다르다 |
| sitemap | 같은 `seo.json`에서 빌드 시 생성 | 손으로 두 군데 적으면 갈라진다 |
| `/api` 크롤 차단 | **하지 않는다** | 막으면 Googlebot 렌더가 빈 화면을 본다. 값이 전부 TTL 캐시 뒤에 있고 이 규모의 크롤 빈도는 낮다. 부하는 020 메트릭으로 지켜보고 **문제가 확인되면 그때** 막는다 |
| 게이트 뒤 화면 | **noindex 안 붙인다** | 검색 결과에 뜨는 것 자체가 017이 말한 "가입 유도"다. 안내문이 서로 비슷한 문제는 정적 `<head>`를 경로마다 다르게 써서 완화한다 |
| 소유권 확인 | **Cloudflare DNS TXT** (도메인 속성) | HTML 파일 방식은 토큰이 저장소에 남고 경로가 하나 더 생긴다. TXT는 서브도메인까지 한 번에 덮는다 |
| JSON-LD | `WebSite` + `Organization`만, 첫 화면에만 | 그 이상은 색인할 콘텐츠가 생긴 뒤의 이야기다 |
| 네이버·다음 | **범위 밖** | 이 문서는 구글이다. 등록 절차가 전혀 다르므로 별도로 다룬다 |

## 알려진 함정 (착수 전에 아는 것)

- **SPA fallback 제거는 딥링크를 깨뜨린다.** `=404`로 바꾸는 순간, 정적 HTML이 구워지지 않은
  경로는 사용자에게도 404다. 라우트를 더하고 `seo.json`을 안 고치면 바로 이 상황이라
  §2의 빌드 가드가 유일한 방어선이다.
- **구글은 즉시 반영되지 않는다.** 색인은 수일~수주다. 배포 다음 날 검색해보고 "안 됐다"고
  판단하면 안 된다. 판단 근거는 검색창이 아니라 서치콘솔이다.
- **Cloudflare 엣지 캐시 — 예상했고, 실제로 밟았다.** 배포 직후 `/robots.txt`가 **배포 전
  HTML**을 내놨다(`cf-cache-status: HIT`, `max-age=14400`). 오리진은 정상이었다 —
  쿼리스트링을 붙이면 `MISS`로 올바른 파일이 나왔다. **`.txt`는 Cloudflare 기본 캐시 확장자고
  `.xml`은 아니라서** sitemap만 멀쩡했다(`DYNAMIC`). 더 고약한 건 **캐시를 채운 게 이 작업
  자신**이라는 점이다 — 착수 전 진단하느라 친 `curl /robots.txt`가 그때의 응답(=index.html)을
  엣지에 4시간짜리로 박았다. **없는 파일을 확인하는 행위가 그 파일의 잘못된 버전을 캐시한다.**
  새 정적 파일을 추가할 때는 배포 후 purge를 전제로 둔다.
  (영향은 제한적이다 — 구글은 HTML robots.txt를 유효 지시문 없음으로 보고 크롤을 허용한다.
  잃는 건 `Sitemap:` 자동 발견 한 줄이고, 서치콘솔 직접 제출이 그걸 대신한다.)
- **`og` 태그는 JS로 고칠 수 없다.** 카톡·슬랙·디스코드 크롤러는 JS를 아예 안 돌린다.
  `useTabTitle` 같은 방식으로는 영원히 안 되고, 정적 `<head>`가 유일한 해결이다.
- **서치콘솔 TXT 레코드는 terraform 밖에 있다.** 기록해두지 않으면 DNS를 손볼 때 지워지고,
  지워지면 소유권 확인이 풀려 데이터가 끊긴다.
- **게이트 뒤 화면 4개는 크롤러 눈에 거의 같은 안내문이다.** 정적 `<head>`가 달라도 본문이
  비슷하면 구글이 하나로 묶을 수 있다. 이건 배관이 아니라 콘텐츠 문제라 여기서 안 풀린다.
- **`/api`를 열어두면 크롤러가 브로커 한도를 먹는다.** 캐시가 앞에 있어 가능성은 낮다고 보지만,
  021에서 본 것처럼 잡 하나가 브로커 호출 70개로 팬아웃하는 구조라 **한 번은 재봐야 한다.**
- **로컬에서 이 이미지는 혼자 못 뜬다.** `nginx.conf`의 `proxy_pass http://backend:8000`을
  nginx가 **기동 시점에** 해석하므로, `backend`가 없으면 `host not found in upstream`으로
  컨테이너가 바로 죽는다(응답이 아니라 연결 거부 `000`이 나온다). 검증할 때는
  `--add-host backend:127.0.0.1`로 띄운다 — 021에서 `503`과 `000`을 갈랐던 것과 같은 자리다.
- **이 작업은 유입을 만들지 않는다.** 배관이 뚫릴 뿐이고, 뚫린 배관으로 흘릴 물은 다음 문서다.
  이걸 혼동하면 2주 뒤 "SEO를 했는데 방문자가 그대로"라는 잘못된 결론이 난다.

## 후속

- **콘텐츠 전략** — 서치콘솔 수치를 보고 셋 중에서 고른다.
  ① 로그인 없이 읽는 설명 페이지(`주도주란`·`필터 12종`·`눌림목 돌파`) — 게이트와 충돌 없음
  ② 공개 데이터로 색인용 URL 늘리기(지수별 일자 페이지) — 롱테일 대신 크롤 부하·저품질 색인 위험
  ③ 게이트 완화 — 유입 최대, 017의 가입 유도 설계를 되돌리는 결정
- **네이버 서치어드바이저·다음** — 국내 서비스라 실제 유입은 여기가 더 클 수 있다
- **Core Web Vitals** — 번들 크기와 LCP를 아직 한 번도 재지 않았다
