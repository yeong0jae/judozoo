# 019 — 관측 스택을 전용 VM으로 분리

Goal: 앱 VM에 얹혀 있는 **Loki·Grafana를 외부 IP 없는 전용 VM**으로 옮긴다. 수집기(`alloy`)는 앱 VM에 남아 네트워크 너머로 push한다. 앱 VM은 destroy 0건으로 보존한다.

> **용량 때문이 아니다.** 관측 3종은 합쳐 247MB고, [018](018-cloud-sql-이관.md)이 끝나면 mysql 604MB가 빠져 앱 VM은 더 한가해진다. 목적은 둘이다 —
> ① **앱 VM이 죽어도 로그가 살아 있다.** 왜 죽었는지 봐야 할 바로 그 순간에 조사 도구가 없는 상태를 없앤다
> ② **배포가 관측을 흔들지 않는다.** 지금은 배포마다 loki·grafana가 강제 재생성된다

## 진입 조건 (2026-09-15 실측)

| 컨테이너 | 메모리 | 이동 |
|---|---|---|
| `alloy` | 95MB | **앱 VM에 잔류** |
| `grafana` | 81MB | → ops VM |
| `loki` | 71MB | → ops VM |
| (참고) backend | 172MB | 잔류 |
| (참고) caddy·frontend | 20MB | 잔류 |

- Loki 보존 **168시간(7일)**, 그 7일치가 `loki-data` **16.8MB** — 로그량이 아주 적다
- `grafana-data` 25.1MB. 단 **대시보드는 파일로 프로비저닝된다**(`observability/grafana/dashboards` 읽기전용 바인드) — 볼륨에 남는 건 사용자 설정뿐이다
- `alloy`는 `unix:///var/run/docker.sock`을 읽는다. **유닉스 소켓이라 원격에서 못 읽는다** — 그래서 수집기는 호스트마다 필요하고, 저장소만 한 곳에 모은다
- 현재 alloy의 push 대상은 `http://loki:3100` (compose 서비스명)
- 방화벽 `auto-trading-allow-ssh` = `tcp:22,3000` ← IAP 대역. 3000은 Grafana용이다

## 설계 결정

| 항목 | 선택 | 이유 |
|---|---|---|
| ops VM 사양 | **e2-small** (2GB) | loki+grafana 실사용 152MB. e2-micro(1GB)도 되지만 Loki 컴팩션이 CPU·메모리를 튀게 해서 여유를 둔다 |
| 외부 IP | **없음** | 관측 도구를 인터넷에 두지 않는다. 017에서 Grafana 공개 서브도메인을 없앤 것과 같은 판단 |
| ops VM의 alloy | **두지 않는다** | 걷을 게 loki·grafana 자기 로그뿐인데, **바로 옆 Loki로 push하므로 Loki가 죽으면 그 사실을 남길 곳도 같이 죽는다.** 반쪽짜리에 95MB를 쓰지 않는다. ops 스택 문제는 SSH + `docker logs`로 본다 |
| 데이터 디스크 | **별도 PD 없음, 부트디스크만** | 대시보드는 git에 있고 로그는 7일짜리다. VM을 재생성해도 잃을 게 사용자 설정과 지난 로그뿐이다. 018에서 PD를 뗀 것과 판단 기준이 다른 이유가 이것이다 |
| 존 | **앱 VM과 같은 존** | 목표는 인스턴스 장애 격리다. 존 장애까지 막으려면 교차 존 이그레스 비용이 붙고, 그건 이번 범위가 아니다 |
| 아웃바운드 | **Cloud NAT** | 외부 IP가 없으면 Docker 설치와 apt 보안 패치가 막힌다 |
| 이름 | `judozoo-ops-prod` · 태그 `judozoo-ops` | 새 리소스는 `judozoo-*` |
| Grafana 접속 | **ops VM으로 IAP 터널** | 앱 VM의 3000은 반납한다 |

### 목표 구성

```
                    인터넷
                      │ 80/443
        ┌─────────────▼──────────────┐
        │ 앱 VM  e2-medium (기존)     │  auto-trading-app-kiwoom-real
        │  caddy / frontend / backend│  tag: auto-trading
        │  alloy ──── push ──┐       │
        └────────────────────┼───────┘
                             │ 3100 (VPC 내부 DNS)
        ┌────────────────────▼───────┐
        │ ops VM  e2-small           │  judozoo-ops-prod
        │ 외부 IP 없음                │  tag: judozoo-ops
        │  loki  ◀───────────┘       │
        │  grafana  (alloy 없음)      │
        └────────────────────┬───────┘
                             │ 아웃바운드만
                        [ Cloud NAT ]

  사람 → Grafana : IAP 터널 → ops VM:3000
  Grafana → MySQL: Cloud SQL private IP (018 이후, 같은 VPC라 그대로 닿는다)
```

내부 DNS: `judozoo-ops-prod.asia-northeast3-a.c.trading-496508.internal`

## 1. 네트워크 — NAT + 방화벽

- [ ] 서브넷 Private Google Access 활성화 — **Terraform 말고 gcloud로.** default 서브넷을 Terraform이 관리하면 import가 필요하다
      ```
      gcloud compute networks subnets update default \
        --region=asia-northeast3 --enable-private-ip-google-access
      ```
- [ ] `main.tf` — `google_compute_router` `judozoo-router` (network `default`)
- [ ] `main.tf` — `google_compute_router_nat`
      - `nat_ip_allocate_option = "AUTO_ONLY"`
      - `source_subnetwork_ip_ranges_to_nat = "ALL_SUBNETWORKS_ALL_IP_RANGES"`
      - `log_config { enable = true, filter = "ERRORS_ONLY" }`
- [ ] `main.tf` — 방화벽 `judozoo-ops-allow-loki`
      - `allow tcp:3100`, `source_tags = ["auto-trading"]`, `target_tags = ["judozoo-ops"]`
- [ ] `main.tf` — 방화벽 `judozoo-ops-allow-iap`
      - `allow tcp:22,3000`, `source_ranges = ["REDACTED_IP/20"]`, `target_tags = ["judozoo-ops"]`
- [ ] `main.tf` — `google_compute_firewall.ssh`(앱 VM)에서 **3000 제거** → `["22"]`로 되돌린다. Grafana가 떠났으므로 열어둘 이유가 없다

> **ops VM에 `auto-trading` 태그를 절대 달지 않는다.** 그 태그는 `auto-trading-allow-web`(0.0.0.0/0 → 80,443)의 타깃이다.

## 2. ops VM 프로비저닝

- [ ] `main.tf` — `google_compute_instance` `ops`
      - `name = "judozoo-ops-prod"`, `machine_type = "e2-small"`, `tags = ["judozoo-ops"]`
      - boot: `ubuntu-2404-lts-amd64`, 20GB
      - `network_interface { network = "default" }` — **`access_config` 블록 없음**
      - `service_account` — 기존 `google_service_account.vm` 재사용 (AR pull·Secret 접근이 이미 있다)
      - `metadata = { enable-oslogin = "TRUE", startup-script = file("startup.sh") }` — 앱 VM과 같은 스크립트를 쓴다(Docker 설치뿐이라 분기가 필요 없다)
- [ ] `outputs.tf` — `ops_vm_name`, `ops_internal_dns` 출력
- [ ] `terraform apply`
- [ ] GitHub Actions Variables에 `VM_NAME_OPS` 추가

## 3. compose 분리

- [ ] `docker-compose.yml` — `loki`·`grafana` 서비스 **제거**. `alloy`는 남긴다
- [ ] `docker-compose.yml` — `loki-data`·`grafana-data` 볼륨 선언 제거
- [ ] `docker-compose.ops.yml` 신설 — `loki` + `grafana`
      - grafana `ports: - "3000:3000"` — IAP 터널이 호스트 포트로 붙는다. **`127.0.0.1`에 묶으면 IAP가 닿지 못한다**
      - loki `ports: - "3100:3100"` — **alloy가 다른 머신에서 붙으므로 호스트에 내야 한다.** compose 네트워크 안에서만 쓰던 때와 달라지는 지점이다
      - 볼륨·바인드 마운트는 기존 정의를 그대로 옮긴다
- [ ] `docker-compose.ops.prod.yml` 신설 — `restart: unless-stopped`
- [ ] `docker-compose.prod.yml` — loki·grafana 관련 항목이 있으면 ops 쪽으로 이동

## 4. alloy → 원격 Loki

- [ ] `observability/alloy/config.alloy` — push 대상을 환경변수로
      ```
      loki.write "default" {
        endpoint {
          url = sys.env("LOKI_PUSH_URL")
        }
      }
      ```
      `sys.env`가 이 버전(v1.7.5)에서 동작하는지 먼저 확인한다. 안 되면 config 파일을 호스트별로 둘로 나눈다
- [ ] `remote_deploy.sh` — `secrets/.env`에 `LOKI_PUSH_URL` 기록
      `http://judozoo-ops-prod.asia-northeast3-a.c.trading-496508.internal:3100/loki/api/v1/push`
- [ ] `docker-compose.yml`의 `alloy`에 해당 환경변수 전달
- [ ] alloy WAL 확인 — ops VM이 잠깐 죽어도 버티다가 재전송하는지. 한도를 넘으면 버린다

> **이 단계를 빠뜨리면 조용히 실패한다.** alloy는 `http://loki:3100`을 못 찾아도 앱을 멈추지 않는다. 증상은 에러가 아니라 **Grafana 대시보드가 비는 것**이다.

## 5. Grafana 데이터소스

- [ ] `provisioning/datasources/loki.yaml` — **그대로 둔다.** Loki와 Grafana가 같은 compose 네트워크에 있으므로 `http://loki:3100`이 계속 맞다
- [ ] `provisioning/datasources/mysql.yaml` — `$DB_HOST`를 쓰도록 이미 018에서 바꿨다. **ops VM의 `secrets/.env`에도 `DB_HOST`·`GF_MYSQL_PASSWORD`가 필요하다**
- [ ] Cloud SQL 도달 확인 — ops VM도 같은 VPC라 피어링 경로가 그대로 열린다
- [ ] 018 §5의 Grafana GRANT 실행 위치 결정 — 앱 VM과 ops VM 중 한 곳에서만 돌게 한다(둘 다면 중복이고, 둘 다 아니면 계정이 안 생긴다)

## 6. 배포 파이프라인

- [ ] `infra/deploy/remote_deploy_ops.sh` 신설
      - Secret Manager → `secrets/.env` (`GF_SECURITY_ADMIN_PASSWORD`, `GF_MYSQL_PASSWORD`, `DB_HOST`)
      - `docker compose -f docker-compose.ops.yml -f docker-compose.ops.prod.yml up -d --remove-orphans`
      - 헬스체크: `curl -fsS localhost:3000/api/health`, `curl -fsS localhost:3100/ready`
- [ ] `remote_deploy.sh`(앱) — `--force-recreate --no-deps loki alloy grafana` → **`alloy`만** 남긴다
- [ ] `remote_deploy.sh`(앱) — `GF_SECURITY_ADMIN_PASSWORD`·`GF_MYSQL_PASSWORD` 기록 제거 (ops로 이동)
- [ ] `deploy.yml` — `deploy-ops` job 신설. scp 대상: `docker-compose.ops*.yml`, `remote_deploy_ops.sh`, `observability/`
- [ ] `deploy.yml` — 앱 job은 그대로 `observability/`를 보낸다 (alloy config 때문)

## 알려진 함정

- **alloy의 push 실패는 에러로 안 나타난다.** 앱은 멀쩡히 돌고 대시보드만 빈다. §4를 빠뜨리면 로그가 조용히 사라진다.
- **`default-allow-internal`이 VPC 내부 전 포트를 이미 열어둔다.** §1의 `judozoo-ops-allow-loki`는 문서로서의 가치는 있지만 실제 경계가 아니다. [017](017-공개-전환-구글-로그인.md)에서 `default-allow-ssh`로 같은 착각을 했다.
- **Grafana를 `127.0.0.1:3000`에 묶으면 IAP가 닿지 못한다.** IAP는 VM의 네트워크 인터페이스로 붙는다.
- **Loki는 호스트 포트가 필요하다.** alloy가 다른 머신에서 붙기 때문이다. compose 네트워크 안에서만 쓰던 때와 다르다.
- **Cloud NAT는 외부 IP가 있는 VM에 적용되지 않는다.** 앱 VM 동작은 변하지 않는다.
- **Private Google Access로는 `download.docker.com`이 안 된다.** googleapis.com 계열만 해당한다.
- **`terraform apply`는 배포 파이프라인에 없다.** `deploy.yml`은 terraform을 돌리지 않는다 — 방화벽·VM 변경은 직접 apply해야 한다.
- **앱 VM의 3000을 닫는 것을 잊지 말 것.** 안 닫으면 쓰지도 않는 포트가 IAP에 열린 채 남는다.
- **같은 존이다.** 존 장애에는 둘 다 죽는다. 이 작업이 막는 것은 인스턴스 단위 장애다.
- **ops VM에 alloy가 없으므로 자기 로그는 Grafana에 안 보인다.** ops 스택이 이상하면 SSH로 `docker logs`를 본다.

## 후속

- ops VM을 다른 존에 두는 안 — 존 장애 대비. 교차 존 이그레스 비용을 먼저 잰다
- Loki 보존 기간 재검토 — 7일치가 17MB라 늘릴 여지가 크다
- 앱 VM 이름을 `judozoo-server-prod`로 (018·019가 끝나면 앱 VM에 상태가 거의 남지 않는다)
- `default-allow-internal` 축소
